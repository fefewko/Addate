# План: убрать `supabase.co` из письма подтверждения email

Дата: 27.11.2026
Статус: **запланировано, не начато**
Область: Supabase Auth (панель), веб-версия, опционально APK
Код и конфигурация на момент сохранения плана не изменялись.

---

## 1. Проблема

При регистрации приходит письмо, ссылка в котором ведёт на:

```
https://<project-ref>.supabase.co/auth/v1/verify?token=<hash>&type=email&redirect_to=addate://auth/callback
```

Это не ссылка на базу данных, а эндпоинт Supabase Auth. В URL нет пароля и
данных анкеты — только одноразовый хеш токена (живёт 1 час, срабатывает один
раз, передаётся по HTTPS). Тем не менее есть реальные минусы:

| Риск | Пояснение |
|---|---|
| Фишинг и доверие | Пользователь не может проверить, что `*.supabase.co` — это ADDate. Похожие домены — классика фишинга. |
| Сканеры почты сжигают ссылку | Microsoft Defender Safe Links и корпоративные фильтры открывают ссылки в письме. Токен одноразовый — пользователь получает «ссылка недействительна». Документированное ограничение Supabase. |
| Зависимость от чужого домена | Смена проекта Supabase = смена домена в письмах. |
| Раскрыт project-ref | Мелочь, но упрощает целевые атаки на конкретный проект. |

Это не уязвимость шифрования, а вопрос бренда, доверия и устойчивости доставки.

---

## 2. Варианты

| Вариант | Как выглядит ссылка | Цена | Правки кода |
|---|---|---|---|
| **A. Custom domain Supabase** | `https://api.addate.ru/auth/v1/verify?...` | Платный add-on на платном плане (Pro+) | Нет, только DNS и панель |
| **B. Свой шаблон письма с `token_hash`** (рекомендуется) | `https://addate.ru/web/auth/confirm?token_hash=...` | Бесплатно | Да: экран подтверждения + `verifyOtp` |
| **C. Только усилить текущую схему** | остаётся `supabase.co` | Бесплатно | Нет |

Рекомендация: **B + элементы C**. Вариант A — запасной, если появится бюджет
на платный план и не хочется трогать код.

---

## 3. Этап 0. Зафиксировать текущее состояние (5 минут)

В панели Supabase:

| Раздел | Что проверить |
|---|---|
| Authentication → URL Configuration | `Site URL`, список `Redirect URLs` |
| Authentication → Emails → Templates → **Confirm signup** | текущий шаблон и тема |
| Authentication → Sign In / Providers → Email | включён ли **Confirm email** |
| Authentication → Emails → SMTP Settings | свой SMTP или встроенный |
| Authentication → Rate Limits | лимиты отправки |
| Logs → Auth | есть ли ошибки `otp_expired` / `token has expired` |

Важно: `supabase/config.toml` в репозитории — только для локального стека.
На hosted-проект он не влияет, всё меняется в панели.

Признак проблемы со сканерами почты: в Auth-логах много `otp_expired` сразу
после отправки письма — ссылку открыл фильтр, а не человек.

---

## 4. Этап 1. Подготовить почтовый домен (если SMTP свой)

- [ ] Отправитель: `no-reply@addate.ru` (или `support@addate.ru`).
- [ ] **SPF**: `v=spf1 include:<провайдер> ~all`.
- [ ] **DKIM**: публичный ключ от провайдера.
- [ ] **DMARC**: `v=DMARC1; p=quarantine; rua=mailto:dmarc@addate.ru`.
- [ ] В почтовом провайдере **отключить трекинг ссылок** — он ломает
      одноразовые токены Supabase.
- [ ] Проверить письмо через mail-tester.com: цель 9–10/10,
      SPF/DKIM/DMARC pass.

Если используется встроенный SMTP Supabase — он ограничен по частоте и не
предназначен для production. Для реального запуска нужен свой.

## 5. Этап 2. Настройки в панели Supabase

### 5.1. URL Configuration

Authentication → URL Configuration:

- **Site URL**: `https://addate.ru/web`
- **Redirect URLs** — точными строками, без wildcard:

```
https://addate.ru/web/auth/callback
https://addate.ru/web/auth/confirm
addate://auth/callback
http://localhost:8081/web/auth/callback
```

Последнюю строку — только для локальной разработки; в production-проекте
лучше не держать.

Проверка: `Site URL` не должен быть `http://localhost:3000` — иначе Supabase
подставит его в письма и fallback-редиректы.

### 5.2. Шаблон Confirm signup

Authentication → Emails → Templates → **Confirm signup**.

Тема:

```
Подтвердите адрес в ADDate
```

Тело:

```html
<h2>Подтверждение адреса</h2>

<p>Здравствуйте!</p>
<p>Вы регистрируетесь в ADDate. Подтвердите адрес, чтобы завершить регистрацию.</p>

<p>
  <a href="https://addate.ru/web/auth/confirm?token_hash={{ .TokenHash }}&amp;type=email"
     style="display:inline-block;padding:12px 20px;background:#2563eb;color:#fff;border-radius:8px;text-decoration:none;">
    Подтвердить адрес
  </a>
</p>

<p style="color:#666;font-size:13px;">
  Если кнопка не открывается, скопируйте ссылку:<br>
  https://addate.ru/web/auth/confirm?token_hash={{ .TokenHash }}&amp;type=email
</p>

<p style="color:#666;font-size:13px;">
  Ссылка действует 1 час и срабатывает один раз.<br>
  Если вы не регистрировались в ADDate, просто проигнорируйте письмо.
</p>
```

Почему так:

- `{{ .TokenHash }}` вместо `{{ .ConfirmationURL }}` — ссылка больше не ведёт
  на `supabase.co`;
- `type=email` — то же значение, что Supabase использует в стандартной ссылке
  подтверждения;
- ссылка ведёт на страницу с кнопкой, а не сразу на верификацию: сканеры почты
  не смогут «сжечь» токен автоматическим переходом;
- запасная текстовая ссылка — для клиентов, которые блокируют кнопки.

Если после смены шаблона подтверждение начнёт возвращать ошибку типа токена —
заменить `type=email` на `type=signup`. Это единственная развилка, проверяется
тестовым письмом.

### 5.3. Проверить, что шаблон применился

- [ ] Зарегистрировать тестовый аккаунт.
- [ ] Открыть исходник письма: в `href` должен быть
      `https://addate.ru/web/auth/confirm?...`, а не `supabase.co`.
- [ ] Убедиться, что тема и текст новые.

До появления страницы `/web/auth/confirm` ссылка будет вести на 404 — это
нормально, пока не выложен этап 3. Этапы 2 и 3 лучше делать вместе.

## 6. Этап 3. Правки в коде (описание, не применено)

Минимальный объём — только веб, **без пересборки APK**:

1. `src/lib/webLinks.ts`:
   - добавить путь `authConfirm: 'auth/confirm'`;
   - добавить `AuthConfirm` в `screensForWeb()`.
2. `src/lib/navigation.ts`:
   - добавить маршрут `AuthConfirm: { token_hash?: string; type?: string }`.
3. Новый `src/screens/AuthConfirm.tsx`:
   - читает `token_hash` и `type` из параметров;
   - показывает кнопку **«Подтвердить адрес»** (верификация только по нажатию);
   - по нажатию вызывает:

     ```ts
     supabase.auth.verifyOtp({ token_hash, type: type as EmailOtpType })
     ```

   - успех: «Адрес подтверждён. Вернитесь в приложение и войдите» + кнопки
     «Открыть приложение» (`addate://`) и «Войти на сайте»;
   - ошибка: «Ссылка устарела или уже использована» + переход на вход;
   - токен нигде не логируется.
4. `src/screens/AuthCallback.tsx`:
   - научить принимать `token_hash` + `type` и вызывать `verifyOtp`;
   - ветку с `code` и `exchangeCodeForSession` оставить для совместимости.

   Этот пункт нужен только если ссылка должна открывать нативное приложение.
   Для подтверждения в браузере он не обязателен, и тогда APK пересобирать
   не нужно.

Проверки: `npx tsc --noEmit`, `npm run build:web`, ручной сценарий.

## 8. Этап 5. Тестирование

| Сценарий | Ожидание |
|---|---|
| Новая регистрация | Письмо со ссылкой на `addate.ru` |

## 9. Этап 6. Откат

- Вернуть в шаблоне `{{ .ConfirmationURL }}` — мгновенно, без выкладки.
- Redirect URLs можно оставить: они не мешают.

  предыдущую версию.

## 10. Альтернатива: платный custom domain

Если решено не трогать код:

1. Project Settings → General → **Custom Domains** → добавить add-on
   (нужен платный план).
2. DNS:
   - `CNAME api.addate.ru → <project-ref>.supabase.co`
     (в Cloudflare — **DNS only**, не proxied);
   - `TXT _acme-challenge.api.addate.ru` — значение выдаст панель/CLI.
3. Дождаться выпуска сертификата (до 30 минут), активировать домен.
4. Supabase Auth сразу начнёт использовать `api.addate.ru` в письмах.
   Клиентский URL можно не менять — оба домена работают.
5. Проверить письмо: ссылка должна начинаться с
   `https://api.addate.ru/auth/v1/verify`.

Ограничения: только поддомен, только CNAME, один домен на проект.

- код и выкладка веб-версии — 1–2 часа;

   `token_hash` в нативное приложение?
